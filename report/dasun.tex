\section{Task 2: Custom Architecture Design}
\label{sec:task2}
\subsection{Custom architecture design}
\label{sec:custom-architecture}

Both custom networks take a $64\times64$ RGB image and output ten class
logits.  Each feature-extraction stage uses a valid (unpadded), stride--1
$3\times3$ convolutional operation, ReLU, and $2\times2$ stride--2 max pooling.
The spatial sizes are
$64\rightarrow62\rightarrow31\rightarrow29\rightarrow14\rightarrow12
\rightarrow6$.  Both networks have channel widths 32, 64, and 128 and hidden
fully connected widths 128 and 64.  Model B replaces Model A's standard
convolutions with depthwise separable convolutions and its flattened head
with global average pooling (GAP).

All convolutional and dense layers have biases.  Neither model uses batch
normalisation.  During training, dropout with probability 0.2 is applied
immediately before each hidden dense layer.  It is disabled for validation
and inference.  The final dense layer outputs logits without a ReLU or
softmax.

A standard convolution has
\begin{equation}
  P_{\mathrm{conv}}=(K_hK_wC_{\mathrm{in}}+1)C_{\mathrm{out}},
\end{equation}
where the added one is one bias per output channel.  A depthwise--pointwise
pair instead has
\begin{equation}
  P_{\mathrm{sep}}=(K_hK_w+1)C_{\mathrm{in}}
  +(C_{\mathrm{in}}+1)C_{\mathrm{out}}.
\end{equation}
A dense layer has $(N_{\mathrm{in}}+1)N_{\mathrm{out}}$ parameters.  For one
image, convolution MACs are counted as
$K_hK_wC_{\mathrm{in}}C_{\mathrm{out}}H_{\mathrm{out}}W_{\mathrm{out}}$
and dense MACs as $N_{\mathrm{in}}N_{\mathrm{out}}$; bias additions are not
counted.  Max pooling, ReLU, dropout, flatten, and GAP have no trainable
parameters.  To match the project profiler exactly, pooling and averaging
operations are also outside the reported MAC total.

100,000-parameter limit.  Keeping a flattened head would leave a
$589{,}952$-parameter first dense layer, already over budget.  GAP lets us
keep the feature-channel widths; narrowing the channels would also reduce
the capacity of the feature extractor.

\subsection{Hardware-aware activation-function choice}
\label{sec:activation-choice}

Models A and B use ReLU, $f(x)=\max(0,x)$, after each convolutional stage and
hidden fully connected layer.  It passes positive values unchanged and sets
negative values to zero.  Positive inputs do not saturate.  Negative inputs
have zero gradient, so a unit can stop learning if it remains inactive
(the dying-ReLU problem).  ReLU outputs are also not zero-centred.

Each model applies ReLU to
\begin{equation}
  32(62^2)+64(29^2)+128(12^2)+128+64=195{,}456
\end{equation}
hidden values per image.  Arm's CMSIS-NN Q7 reference implementation compares
each scalar with zero and assigns zero to negative values.  On DSP-capable
M-profile cores, its vector path masks four signed 8-bit values per loop
iteration.\footnote{Arm Ltd., \emph{CMSIS-NN
\texttt{arm\_relu\_q7.c}}, lines 50--101,
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Source/ActivationFunctions/arm_relu_q7.c}.}
The arithmetic requires no coefficients or lookup table.  Loads, stores and
loop control still contribute to the cycle count, which depends on the core
and compiler.

Sigmoid and tanh require exponentials or an approximation:
\begin{equation}
  \sigma(x)=\frac{1}{1+e^{-x}}, \qquad
  \tanh(x)=\frac{e^x-e^{-x}}{e^x+e^{-x}},
\end{equation}
Both functions saturate at extreme inputs, where their gradients approach
zero.  In CMSIS-NN, the 16-bit implementations use a 256-entry
\texttt{uint16\_t} sigmoid table.  Inputs within its range need two table
reads and integer interpolation; inputs outside the range take a saturation
branch.  The table occupies $256\times2=512$ bytes of read-only memory,
before code and temporary values.\footnote{Arm Ltd., \emph{CMSIS-NN
\texttt{arm\_nn\_activation\_s16.c}}, lines 51--117, and
\texttt{arm\_nn\_tables.h}, line 40,
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Source/ActivationFunctions/arm_nn_activation_s16.c},
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Include/arm_nn_tables.h}.}
Using these functions at every hidden site would require 195,456 such
evaluations per image.  These integer kernels are examples of embedded
implementations; our experiments use floating-point PyTorch kernels.

Core support also affects floating-point cost.  Arm describes the Cortex-M4/M7
FPU as optional and compares hardware floating point with emulation using
integer operations.\footnote{Arm Ltd.,
\emph{DSP capabilities of Cortex-M4 and Cortex-M7}, 2016, pp.~4--5,
\url{https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/white-paper-dsp-capabilities-of-cortex-m4-and-cortex-m7}.}
The activation comparison here is analytical.  We did not measure
microcontroller inference latency.

GELU's exact form, $x\Phi(x)$, uses the Gaussian cumulative distribution
(equivalently an error function); its common approximation uses tanh.\footnote{D. Hendrycks and
K. Gimpel, \emph{Gaussian Error Linear Units (GELUs)}, 2016,
\url{https://arxiv.org/abs/1606.08415}.}
Leaky ReLU and PReLU keep a nonzero gradient on the negative branch when the
slope is nonzero, at the cost of a multiply on that branch.  PReLU also learns
and stores the slope $\alpha$.  We chose ReLU for its simpler inference
operation.  We did not compare activation functions experimentally.

\subsubsection{ReLU6 and low-precision deployment}

MobileNetV2 uses
$\operatorname{ReLU6}(x)=\min(\max(0,x),6)$ for its robustness in low-precision
computation.\footnote{M. Sandler et al.,
\emph{MobileNetV2: Inverted Residuals and Linear Bottlenecks}, Section~4,
\url{https://arxiv.org/abs/1801.04381}.}
The upper bound limits the represented range, allowing integer levels to be
spaced more closely within it.  CMSIS-NN provides a signed-8-bit ReLU6
operator.  Our custom models use floating point, and quantisation is outside
this project's scope.  We kept ordinary ReLU so that values above six remain
available to the next layer.

\subsubsection{Output probabilities}

Softmax converts the ten output logits to normalised probabilities:
\begin{equation}
  p(y=C_k\mid x)=\frac{\exp(z_k)}{\sum_{j=1}^{10}\exp(z_j)}.
\end{equation}
This requires ten exponentials per image.  Applying an exponential-based
activation to all 195,456 hidden values would involve approximately
19,546 times as many values.

The models return raw logits to \texttt{CrossEntropyLoss} during training.
At inference, the class prediction is the index of the largest logit;
softmax preserves this ordering.  Softmax is needed only to report
normalised probabilities, and it does not by itself establish calibration.
The hidden layers use ReLU throughout.

\section{Task 3: Optimizer Selection and Tuning}
\label{sec:task3}
\subsection{Optimizer comparison protocol}
\label{sec:optimizer-comparison}

We trained Model~B with Adam at $\alpha=10^{-3}$, plain stochastic gradient
descent (SGD) at $\alpha=10^{-2}$, and SGD at the same learning rate with
momentum $m=0.9$.  The model, split manifest, seed, data order, batch size and
augmentation were the same across runs.  Each run used seed 42, batch size
128, 30 epochs, zero weight decay, and a fixed learning rate without a
scheduler.  The sweep checks these shared settings before training.  The
saved Adam configuration uses \texttt{device: auto} and the SGD configurations
use \texttt{device: cuda}; all three profiles record a Tesla T4.

SGD updates the weights by
\begin{equation}
  w \leftarrow w-\alpha\frac{\partial L(w)}{\partial w},
\end{equation}
With momentum, the update is
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v.
\end{equation}
Comparing $m=0$ and $m=0.9$ at the same SGD learning rate isolates the effect
of momentum.  Adam uses running first and second moments of the gradients
to scale each parameter's step.  We used its default coefficients,
$\beta_1=0.9$, $\beta_2=0.999$, and $\epsilon=10^{-8}$.

The learning rates $10^{-3}$ for Adam and $10^{-2}$ for SGD were starting
values for this comparison.  We did not run a learning-rate search for each
optimizer.  The results therefore apply to these configurations and this
training budget; each configuration was tested with one seed.

We selected Adam at $\alpha=10^{-3}$ for the custom-model runs because it
had the lowest validation loss (Table~\ref{tab:optimizer-comparison}).  It
also had the highest selected-checkpoint validation accuracy and test
accuracy among the three runs.  SGD with momentum reduced validation loss
faster than plain SGD over the 30 epochs.  For every run, the reported
metrics come from the lowest-validation-loss checkpoint.  Test accuracy
was used only for final evaluation.

\subsection{Effect of the momentum coefficient}
\label{sec:momentum-ablation}

We compared SGD with $m\in\{0,0.5,0.9,0.99\}$ at the fixed learning
rate $\alpha=10^{-2}$.  The split, seed, data order, augmentation, batch size,
initialisation and 30-epoch budget were identical.  All four runs used an
NVIDIA GeForce RTX~3060 Laptop GPU.  Figure~\ref{fig:momentum-ablation}
uses the separate \texttt{momentum\_m000}, \texttt{momentum\_m050},
\texttt{momentum\_m090}, and \texttt{momentum\_m099} records.  Their epoch
times cannot be compared directly with the T4 runs in
Table~\ref{tab:optimizer-comparison}.

In the momentum update,
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v,
  \label{eq:momentum-update}
\end{equation}
$m$ determines how much of the previous velocity is kept.  Gradients with a
consistent sign accumulate in $v$, increasing movement in that direction.
Across a narrow loss ravine, alternating gradient components cancel part of
the stored velocity, damping side-to-side motion.

With $m=0$, the update has no memory and validation loss stays high over the
epoch budget.  At $m=0.5$, loss falls sooner but is still high after 30 epochs.
At $m=0.9$, validation loss falls with small epoch-to-epoch fluctuations
and reaches the lowest value.  At $m=0.99$, loss falls fastest initially,
then fluctuates during later epochs and finishes above its selected minimum.
Keeping more past velocity could explain these fluctuations, but the saved
loss curves do not record gradient directions or establish overshooting.

We selected $m=0.9$ by validation loss.  The slightly higher test accuracy
at $m=0.99$ did not affect that choice.  This ranking is based on one run per
setting; its consistency across random seeds has not been measured.
