\section{Task 2: Custom Architecture Design}
\label{sec:task2}
\subsection{Custom architecture design}
\label{sec:custom-architecture}

Both custom networks accept a $64\times64$ RGB image and produce ten class
logits.  Each feature-extraction
stage uses a valid (unpadded), stride--1 $3\times3$ convolutional
operation, ReLU, and $2\times2$ stride--2 max pooling.  Thus the spatial sequence is
$64\rightarrow62\rightarrow31\rightarrow29\rightarrow14\rightarrow12
\rightarrow6$.  Both networks use channel widths 32, 64, and 128 and hidden
fully connected widths 128 and 64.  This holds the representation widths fixed
so that the resource difference comes from two deliberate substitutions:
standard convolution by depthwise separable convolution, and flattening by
global average pooling (GAP).  Both models use biases in all convolutional
and dense layers, no batch normalisation, and dropout with probability 0.2
immediately before each hidden dense layer during training.  Dropout is
disabled for validation and inference.  The final dense layer returns logits
without a ReLU or softmax.

A standard convolution has
\begin{equation}
  P_{\mathrm{conv}}=(K_hK_wC_{\mathrm{in}}+1)C_{\mathrm{out}},
\end{equation}
where the added one is one bias per output channel.  A depthwise--pointwise
pair instead has
\begin{equation}
  P_{\mathrm{sep}}=(K_hK_w+1)C_{\mathrm{in}}
  +(C_{\mathrm{in}}+1)C_{\mathrm{out}}.
\end{equation}
A dense layer has $(N_{\mathrm{in}}+1)N_{\mathrm{out}}$ parameters.  For one
image, convolution MACs are counted as
$K_hK_wC_{\mathrm{in}}C_{\mathrm{out}}H_{\mathrm{out}}W_{\mathrm{out}}$
and dense MACs as $N_{\mathrm{in}}N_{\mathrm{out}}$; bias additions are not
counted.  Max pooling, ReLU, dropout, flatten, and GAP have no trainable
parameters.  To match the project profiler exactly, pooling and averaging
operations are also outside the reported MAC total.

\subsection{Hardware-aware activation-function choice}
\label{sec:activation-choice}

Models A and B use the rectified linear unit (ReLU),
$f(x)=\max(0,x)$, after every convolutional stage and hidden fully connected
layer.  ReLU provides computationally efficient thresholding and does not
saturate for positive inputs.  Its limitations are that negative units have zero gradient
and can become ``dying ReLUs'', and the output is not zero-centred.  These are
training risks, but neither changes the inference operation: compare with zero
and retain either zero or the input value.

The hardware consequence is substantial because activation cost is paid for
every feature value, not once per layer.  From the implemented output shapes,
each custom model evaluates
\begin{equation}
  32(62^2)+64(29^2)+128(12^2)+128+64=195{,}456
\end{equation}
hidden activation values per image.  Arm's CMSIS-NN Q7 reference ReLU implements
each scalar as a negative comparison followed by assignment of zero; on
DSP-capable M-profile cores its vector path masks four signed 8-bit values per
loop iteration.\footnote{Arm Ltd., \emph{CMSIS-NN
\texttt{arm\_relu\_q7.c}}, lines 50--101,
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Source/ActivationFunctions/arm_relu_q7.c}.}
Thus ``one comparison'' describes the logical arithmetic, although real cycle
counts also include loads, stores and loop control and depend on the core and
compiler.  ReLU needs no coefficients, transcendental unit or lookup table.

Sigmoid and tanh are less attractive here for both learning and deployment.
Their definitions,
\begin{equation}
  \sigma(x)=\frac{1}{1+e^{-x}}, \qquad
  \tanh(x)=\frac{e^x-e^{-x}}{e^x+e^{-x}},
\end{equation}
require exponential evaluation or an approximation.  Both saturate, producing near-zero gradients at the
extremes.  A representative embedded alternative illustrates the memory--time
trade-off: CMSIS-NN implements 16-bit sigmoid and tanh using a
256-entry \texttt{uint16\_t} sigmoid table.  Non-saturated inputs use two table reads and integer
interpolation; inputs outside the table range use a saturation branch.  The table alone occupies $256\times2=512$ bytes of read-only memory,
before code and temporary values.\footnote{Arm Ltd., \emph{CMSIS-NN
\texttt{arm\_nn\_activation\_s16.c}}, lines 51--117, and
\texttt{arm\_nn\_tables.h}, line 40,
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Source/ActivationFunctions/arm_nn_activation_s16.c},
\url{https://github.com/ARM-software/CMSIS-NN/blob/71cbe3d5a686c875c88a4d112633b13fae94b5a2/Include/arm_nn_tables.h}.}
Using either function at all hidden sites would therefore require 195,456
lookup/interpolation or saturation evaluations per image instead of applying
a threshold.  These integer kernels illustrate possible embedded costs;
they are not the floating-point PyTorch kernels used in our experiments.

Floating-point support also depends on the target core.  Arm describes the
Cortex-M4/M7 floating-point unit as optional and contrasts hardware floating
point with emulation using integer operations.\footnote{Arm Ltd.,
\emph{DSP capabilities of Cortex-M4 and Cortex-M7}, 2016, pp.~4--5,
\url{https://developer.arm.com/community/arm-community-blogs/b/architectures-and-processors-blog/posts/white-paper-dsp-capabilities-of-cortex-m4-and-cortex-m7}.}
This supports avoiding unnecessary floating-point transcendental operations;
it does not provide a measured activation latency for our models.  No
microcontroller inference benchmark was performed.

GELU was also rejected.  Its exact form $x\Phi(x)$ uses the Gaussian cumulative
distribution (equivalently an error function), while its common approximation
uses tanh; either is more involved than thresholding.\footnote{D. Hendrycks and
K. Gimpel, \emph{Gaussian Error Linear Units (GELUs)}, 2016,
\url{https://arxiv.org/abs/1606.08415}.}
Leaky ReLU and PReLU are computationally efficient alternatives that
retain a nonzero negative-side gradient when the slope is nonzero, but
require a multiply on the negative branch; PReLU additionally stores and learns the slope $\alpha$.
Without evidence that dying ReLUs impair these models, those extra operations
and parameters are not justified.

\subsubsection{ReLU6 and low-precision deployment}

MobileNetV2 uses
$\operatorname{ReLU6}(x)=\min(\max(0,x),6)$ because the bounded activation is
robust under low-precision computation.\footnote{M. Sandler et al.,
\emph{MobileNetV2: Inverted Residuals and Linear Bottlenecks}, Section~4,
\url{https://arxiv.org/abs/1801.04381}.}
The upper bound prevents rare large activations from expanding the represented
range, so a fixed number of integer levels can cover the useful interval more
densely.  This is directly relevant to int8 deployment and explains why Arm
CMSIS-NN provides a dedicated signed-8-bit ReLU6 operator.  However, this
project makes the edge argument analytically and does not perform
quantisation.  The custom models are trained and evaluated in floating point,
so imposing an upper saturation at six would discard positive magnitude
without delivering a required int8 benefit.  Ordinary ReLU therefore matches
the present deployment scope; ReLU6 is a
future quantised-deployment option rather than the chosen activation.

\subsubsection{The softmax exception}

The ten-class output is the one place where exponentials are justified when
normalised probabilities are required:
\begin{equation}
  p(y=C_k\mid x)=\frac{\exp(z_k)}{\sum_{j=1}^{10}\exp(z_j)}.
\end{equation}
This softmax is evaluated once over ten logits: ten exponentials per image,
not once over a feature map.  Replacing all hidden ReLUs by an exponential-based
activation would apply the expensive operation to 195,456 values, approximately
19,546 times as many values as the output softmax.

The PyTorch models deliberately return raw logits.  During training,
\texttt{CrossEntropyLoss} consumes those logits directly, avoiding a separate
softmax layer.  During inference, softmax is needed only when normalised class
probabilities must be reported; softmax alone does not establish calibration.
For classification, the predicted class itself is the index of the
largest logit because softmax preserves ordering.  Consequently, the necessary
probability normalisation is confined to a ten-value output stage,
while the high-volume hidden activations retain the comparison-only ReLU.

\section{Task 3: Optimizer Selection and Tuning}
\label{sec:task3}
\subsection{Optimizer comparison protocol}
\label{sec:optimizer-comparison}

The optimizer comparison uses Model~B under three configurations: Adam with
$\alpha=10^{-3}$, plain stochastic gradient descent (SGD) with
$\alpha=10^{-2}$, and SGD with the same learning rate and momentum $m=0.9$.
Only the optimizer block changes; the model, split manifest, random seed, data
order, batch size, augmentation, epoch budget, and execution device are held
constant.  The sweep checks the planned configuration equality before
training.  The committed Adam run records \texttt{device: auto}, whereas the
SGD runs record \texttt{device: cuda}; their profiles confirm the same
effective Tesla T4 device.  All use seed 42, batch size 128, 30 epochs,
zero weight decay, and a fixed learning rate without a scheduler.

The SGD update is
\begin{equation}
  w \leftarrow w-\alpha\frac{\partial L(w)}{\partial w},
\end{equation}
while momentum adds a velocity term,
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v.
\end{equation}
The momentum value $0.9$ is therefore compared against $m=0$ without changing
SGD's learning rate.  Adam is evaluated at its own family-appropriate learning
rate rather than forcing all optimizers to share a numerically equal step
size: Adam adapts each parameter's step using running first and second moments
of the gradients, whereas SGD uses the same fixed learning-rate scale for
every parameter.  The implementation uses Adam's default coefficients
$\beta_1=0.9$, $\beta_2=0.999$, and $\epsilon=10^{-8}$.  The selected
starting values, $10^{-3}$ for Adam and
$10^{-2}$ for SGD, are conventional baselines for this comparison and are
recorded in the resolved configuration of every run.  This compares three
specified optimizer configurations, not each optimizer after an equally
exhaustive learning-rate search.  With one seed per configuration, the
observed ranking is evidence for this training budget, not a general claim
that Adam outperforms tuned SGD.

Adam at $\alpha=10^{-3}$ is selected for the final custom-model runs.  As shown
in Table~\ref{tab:optimizer-comparison}, it achieved the lowest validation loss
and the highest validation accuracy at the selected checkpoint and test
accuracy among these three configurations.  Momentum made SGD competitive
relative to plain SGD within this budget; accumulating past gradients can
maintain progress in consistent descent directions.  Plain SGD converged
much more slowly within the same 30-epoch budget.  The choice is based on validation loss rather than test
accuracy, and the reported test accuracies are used only for final evaluation.
Each run uses the same lowest-validation-loss checkpoint rule, so its
reported metrics refer to the selected checkpoint rather than a potentially
poorer final epoch.

\subsection{Effect of the momentum coefficient}
\label{sec:momentum-ablation}

To isolate the effect of momentum, Model~B was trained with SGD at the fixed
learning rate $\alpha=10^{-2}$ for $m\in\{0,0.5,0.9,0.99\}$.  Every other
resolved setting---including the split, seed, data order, augmentation, batch
size, initialization, and 30-epoch budget---was identical.  All four runs were
also timed on the same NVIDIA GeForce RTX~3060 Laptop GPU, so device variation
cannot explain the differences within Figure~\ref{fig:momentum-ablation}.
These are the separate \texttt{momentum\_m000}, \texttt{momentum\_m050},
\texttt{momentum\_m090}, and \texttt{momentum\_m099} runs, not the T4
runs in Table~\ref{tab:optimizer-comparison}; epoch times must not be
compared across these two device groups.

The momentum update,
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v,
  \label{eq:momentum-update}
\end{equation}
shows that $m$ controls how much of the previous velocity survives.  When
successive gradients have a consistent sign, their contributions accumulate
in $v$, increasing progress along that direction.  Across a narrow loss
ravine, gradient components that alternate sign instead cancel part of the
stored velocity, damping side-to-side oscillation while preserving progress
along the ravine.

The validation curves are consistent with faster convergence from momentum,
but do not measure gradient directions or velocity directly.  With $m=0$,
Equation~\ref{eq:momentum-update} has no memory and validation loss remains high within the epoch budget.
Setting $m=0.5$ provides some carry-over and converges faster, but still leaves
substantial loss after 30 epochs.  The $m=0.9$ run descends with only small epoch-to-epoch fluctuations and reaches
the lowest validation loss, making it the preferred momentum setting under the
fixed budget.  At $m=0.99$, validation loss falls fastest initially but
fluctuates during later epochs and finishes above its selected minimum.  Retaining more past velocity
is a plausible explanation for this behaviour, but these loss curves alone
do not establish that individual updates overshot a local minimum.
Although that run happens to obtain a slightly higher test accuracy, it is not
selected on the test split; optimizer selection uses validation loss to avoid
biasing the final evaluation.

Thus momentum is not simply ``more is better'': too little fails to exploit
consistent gradients, while too much retains stale velocity and can destabilise
convergence.  Among these four single-seed runs at the fixed learning rate,
$m=0.9$ attains the lowest validation loss.  Repeated runs would be needed to assess
the stability of this ranking across random seeds.
