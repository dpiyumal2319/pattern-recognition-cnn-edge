\subsection{Optimizer comparison protocol}
\label{sec:optimizer-comparison}

The optimizer comparison uses Model~B under three configurations: Adam with
$\alpha=10^{-3}$, plain stochastic gradient descent (SGD) with
$\alpha=10^{-2}$, and SGD with the same learning rate and momentum $m=0.9$.
Only the optimizer block changes; the model, split manifest, random seed, data
order, batch size, augmentation, epoch budget, and execution device are held
constant.  The sweep checks the planned configuration equality before
training.  The committed Adam run records \texttt{device: auto}, whereas the
SGD runs record \texttt{device: cuda}; their profiles confirm the same
effective Tesla T4 device.  All use seed 42, batch size 128, 30 epochs,
zero weight decay, and a fixed learning rate without a scheduler.

The SGD update is
\begin{equation}
  w \leftarrow w-\alpha\frac{\partial L(w)}{\partial w},
\end{equation}
while momentum adds a velocity term,
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v.
\end{equation}
The momentum value $0.9$ is therefore compared against $m=0$ without changing
SGD's learning rate.  Adam is evaluated at its own family-appropriate learning
rate rather than forcing all optimizers to share a numerically equal step
size: Adam adapts each parameter's step using running first and second moments
of the gradients, whereas SGD uses the same fixed learning-rate scale for
every parameter.  The implementation uses Adam's default coefficients
$\beta_1=0.9$, $\beta_2=0.999$, and $\epsilon=10^{-8}$.  The selected
starting values, $10^{-3}$ for Adam and
$10^{-2}$ for SGD, are conventional baselines for this comparison and are
recorded in the resolved configuration of every run.  This compares three
specified optimizer configurations, not each optimizer after an equally
exhaustive learning-rate search.  With one seed per configuration, the
observed ranking is evidence for this training budget, not a general claim
that Adam outperforms tuned SGD.

Adam at $\alpha=10^{-3}$ is selected for the final custom-model runs.  As shown
in Table~\ref{tab:optimizer-comparison}, it achieved the lowest validation loss
and the highest validation accuracy at the selected checkpoint and test
accuracy among these three configurations.  Momentum made SGD competitive
relative to plain SGD within this budget; accumulating past gradients can
maintain progress in consistent descent directions.  Plain SGD converged
much more slowly within the same 30-epoch budget.  The choice is based on validation loss rather than test
accuracy, and the reported test accuracies are used only for final evaluation.
Each run uses the same lowest-validation-loss checkpoint rule, so its
reported metrics refer to the selected checkpoint rather than a potentially
poorer final epoch.

\subsection{Effect of the momentum coefficient}
\label{sec:momentum-ablation}

To isolate the effect of momentum, Model~B was trained with SGD at the fixed
learning rate $\alpha=10^{-2}$ for $m\in\{0,0.5,0.9,0.99\}$.  Every other
resolved setting---including the split, seed, data order, augmentation, batch
size, initialization, and 30-epoch budget---was identical.  All four runs were
also timed on the same NVIDIA GeForce RTX~3060 Laptop GPU, so device variation
cannot explain the differences within Figure~\ref{fig:momentum-ablation}.
These are the separate \texttt{momentum\_m000}, \texttt{momentum\_m050},
\texttt{momentum\_m090}, and \texttt{momentum\_m099} runs, not the T4
runs in Table~\ref{tab:optimizer-comparison}; epoch times must not be
compared across these two device groups.

The momentum update,
\begin{equation}
  v \leftarrow mv-\alpha\frac{\partial L(w)}{\partial w},
  \qquad w \leftarrow w+v,
  \label{eq:momentum-update}
\end{equation}
shows that $m$ controls how much of the previous velocity survives.  When
successive gradients have a consistent sign, their contributions accumulate
in $v$, increasing progress along that direction.  Across a narrow loss
ravine, gradient components that alternate sign instead cancel part of the
stored velocity, damping side-to-side oscillation while preserving progress
along the ravine.

The validation curves are consistent with faster convergence from momentum,
but do not measure gradient directions or velocity directly.  With $m=0$,
Equation~\ref{eq:momentum-update} has no memory and validation loss remains high within the epoch budget.
Setting $m=0.5$ provides some carry-over and converges faster, but still leaves
substantial loss after 30 epochs.  The $m=0.9$ run descends steadily and reaches
the lowest validation loss, making it the preferred momentum setting under the
fixed budget.  At $m=0.99$, validation loss falls fastest initially but
fluctuates during later epochs and finishes above its selected minimum.  Retaining more past velocity
is a plausible explanation for this behaviour, but these loss curves alone
do not establish that individual updates overshot a local minimum.
Although that run happens to obtain a slightly higher test accuracy, it is not
selected on the test split; optimizer selection uses validation loss to avoid
biasing the final evaluation.

Thus momentum is not simply ``more is better'': too little fails to exploit
consistent gradients, while too much retains stale velocity and can destabilise
convergence.  Among these four single-seed runs at the fixed learning rate,
$m=0.9$ attains the lowest validation loss.  Repeated runs would be needed to assess
the stability of this ranking across random seeds.
